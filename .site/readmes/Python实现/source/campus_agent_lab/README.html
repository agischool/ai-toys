校园助手规则模拟实验（第 17—20 期）

用固定校园资料逐步展示工具调用、多步流程、输入组织和结果验收。所有学校、公告、场地、需求与故障都是原创构造材料。程序只用 Python 标准库，没有调用真实模型，不访问网络、不执行终端工具，也不执行预约。

运行结果可证明这些规则分支怎样执行，不能证明语言模型能选择相同步骤，也不是 CS329Z 作业的实现或模型测评复现。

运行与保存

需要 Python 3.11+，无须安装依赖。在仓库根目录运行：

python3 Python实现/source/campus_agent_lab/lab.py --episode 17
python3 Python实现/source/campus_agent_lab/lab.py --episode 18
python3 Python实现/source/campus_agent_lab/lab.py --episode 19
python3 Python实现/source/campus_agent_lab/lab.py --episode 20

默认在本目录 outputs/runs/ 中创建带 UTC 时间的独立目录，同时打印结果。自行指定目录时：

python3 Python实现/source/campus_agent_lab/lab.py --episode 17 --output /tmp/campus-17-new-run

指定目录必须尚不存在；即使是空目录，程序也拒绝写入。每次生成 result.json，不覆盖历史输出。outputs/reference/ 保存本版本可复核的四份固定结果；生成结果不含时间戳，因此正文相同。不要将重跑目标指向已有参考目录。

共享资料

资料源文件是 fixtures.py。

资料 内容 范围
D1 图书馆工作日 12:00—18:00 开放，周末闭馆 本学期常规安排，不说明临时检修或明年安排
V1 科学活动室 周二 15:00—17:00；有投影仪、有坡道 本学期；时间来源 S1，详情来源 E1
V2 阅览活动室 周二 15:00—17:00；有投影仪、无坡道 本学期；时间来源 S2，详情来源 E2
场地任务 本学期周二 15:00—16:00，需要投影仪且必须有坡道 只给场地建议，不预约

第 18、20 期部分案例会明确修改资料来制造缺失、冲突、过期等情形，输出逐例附上实际环境和需求。None 表示未知资料，不能等同于空设备表 [] 或明确无坡道 False。

每期观察什么

17：请求不等于执行成功

请求使用 request_id、tool、args。返回保留这些字段，并加入 executed、status、result。

案例 编号 状态 结果
成功 Q1 ok D1 公告
明年无匹配 Q2 ok 空列表；查询完成，没有匹配材料
缺少设施参数 Q3 invalid_args executed=false，没有查询
故意注入读取故障 Q4 tool_error executed=true，尝试执行但未完成

公告工具名为 search_announcements，参数为 facility 和 period。未注册名称会返回 unknown_tool。这里的回答文本由固定规则选择，不是模型生成；查询参数、公告与回答的对应关系可以人工核对。

查看第 17 期固定结果。

18：下一步由固定规则决定

search_venues(period, day, start, end) 查时段覆盖任务的候选；read_details(venue_id) 查设备和坡道。先查时间、再读详情、再比较条件，这个顺序写在代码里。

案例 退出状态 实际工具执行次数 建议
资料完整 suggested 2 V1 科学活动室
V1 设备表未知 insufficient_evidence 2 无；停止补证据
重复相同查询 blocked_repeat 1 无；重复请求被拦
只准执行一步 blocked_step_limit 1 无；详情未查，不宣称完成

重复请求与超限请求也进入 trace，但 executed=false，不算实际工具执行。默认最多 4 次工具执行是教学设置，不是行业标准。缺资料时本例采取保守停止策略，不代表只能采用这一种策略。

查看第 18 期固定结果。

19：只检查硬性条件是否还在输入里

六张原始卡片依次是：C1 坡道要求、C2 时段、C3 投影仪要求、C4 V1 资料、C5 V2 资料、C6 只建议不预约。程序比较全文六卡、末三卡、人工好摘要、人工漏坡道摘要、按条件字段检索后附场地结果五种组织方式。

末三卡虽然还有「V1 有坡道」这一事实，却没有「必须有坡道」这一用户要求。程序检查固定教学文本中的关键短语，列出 requirements_present；它不能评价任意改写的语义正确性。两份摘要都由人编写，不是模型输出。字符数不是 token 数，条件保留下来也不等于模型能用对。

查看第 19 期固定结果。

20：建议要逐项验收

verify_run 重新对照任务、资料和成功执行记录，分别检查时期、星期、完整时段、设备、坡道、资料冲突、时间证据、详情证据及行为范围。建议分支不会只读 status 或案例期望标签来判成功。停止分支另外检查预设案例对应的停止原因，不能把「没有建议」都算合理停止。

输出包含 6 个开发案例和另编的 6 个保留对照案例，逐例显示实际环境、任务、轨迹、调用次数、各项检查和结果：

结果 含义
task_success 建议满足全部条件并有本次工具记录支持
appropriate_stop 该构造情形下说明原因并停止，没有完成原场地任务
incorrect_completion 给了建议，却没通过条件或证据检查
incorrect_result 不该停止却停止，或停止原因与该案例不符

本版开发组与保留组各为 1 例任务成功、5 例恰当停止。这不是任务成功率 100%：每组只有 1 个任务给出合格建议，其余没有完成场地选择。

此外，fault_demo 单独构造「忽略坡道要求」的错误策略：它查得 V2 无坡道，却仍建议 V2。验收的 ramp=false 会把它判为错误完成，其他时间与设备检查仍可通过。这是故意注入的教学错误，不是实际模型失误记录。

这 12 个例子目前都是公开材料，已经共同进入代码回归。名称「保留」表示它们在教学结构中的角色，不能证明开发时未看过；本实验不宣称盲测、独立模型评估或现实系统可靠性。修改规则后继续使用同一组题，属于回归检查；要做独立评估须另备未用于开发的新题。
