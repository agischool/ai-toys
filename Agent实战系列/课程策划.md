# Agent 实战系列策划：以 Karpathy 原始仓库为主线

策划与源码核查日期：2026-11-13。**篇数待定，不预设十篇，也不按七个仓库机械分成七篇。** 本轮只做来源核查和内容设计，尚未运行这里的原仓库训练或 Agent 实验。

## 系列要回答的问题

一个编程 Agent 接到「让训练实验变得更好」的要求后，究竟能改哪里，怎样运行，凭什么判断这次改动值得保留？

以 Andrej Karpathy 的 **autoresearch 为核心案例、nanochat 为训练底座参照**，从真实文件和实验记录解释这个问题。micrograd、minbpe 和 Zero to Hero 补足必要基础；nanoGPT 用作旧版代码对照；llm.c 留作底层实现进阶。它们不是七个同类 Agent 应用，也不是每位读者都要逐一完成的必修链。

本系列暂名「Agent 实战」，副标题和对外介绍都保留「基于 Andrej Karpathy 开源项目」。文章标注具体原仓库及固定版本，不使用「Karpathy 官方课程」「作者亲授」或未经支持的效果承诺。

## 原作、改编与补充资料的关系

| 层次 | 来源 | 怎样使用 |
| --- | --- | --- |
| 主项目 | `karpathy/autoresearch` | 实验协议、训练入口、固定评测、日志和 Git 保留／撤回流程是核心内容依据 |
| 训练底座 | `karpathy/nanochat` | 理解自动实验的训练机制和可改因素；按所选任务阅读对应训练、评测及运行脚本 |
| 前置基础 | `karpathy/micrograd`、`karpathy/minbpe`、`karpathy/nn-zero-to-hero` | 根据读者缺口选入；去掉课程与独立仓库的重复内容 |
| 对照和进阶 | `karpathy/nanoGPT`、`karpathy/llm.c` | 服务于某个具体比较，不作为主线额外必修仓库 |
| 补充对照 | CS329Z 作业及必要的原始研究 | 帮助检查评测有效性、执行记录和边界；不替代 Karpathy 项目，不另造服务台项目主线 |

事实依据优先看固定提交中的源码和运行脚本，再看 README 与作者说明；社交帖不承担代码行为与成本结论。源码和 README 有出入时，先记录差异，依据所选版本解释，不拼接不同版本的数字。

原仓库核查记录集中在 [源仓库核查](源仓库核查/README.md)。它们记录已读范围与未运行事项，不能代替我们自己的复现实验。

进入 autoresearch 主线需要理解相关训练与评测，不要求先完成 nanochat 的全规模训练、全部 SFT/RL，或 llm.c 的 C/CUDA 复现。主线问题决定要读哪些底座代码，其他工作包可以跳过或另作支线。

## 按源码安排内容，不先排文章编号

以下是待制作的**工作包**，不是篇目表。一个工作包可能合并进一篇，也可能在代码阅读与实测后拆开。

| 源码工作包 | 要讲清的问题 | 对应原仓库及入口 | 形成什么证据 | 拆并依据 |
| --- | --- | --- | --- | --- |
| 梯度与更新基础 | 损失怎样影响参数，怎样检查一次更新 | micrograd 的 `Value`、反向传播与网络例子；Zero to Hero 对应课程 | 可复算梯度、有限差分或一次更新的记录 | 已懂自动微分则作选读；不重复写课程与独立仓库两套入门 |
| 分词和训练输入 | 字符串怎样变成 token，为什么编码与解码要核对 | minbpe 的 Basic/Regex 分词器；nanochat 的分词与数据入口 | 输入、词表／合并规则、编码解码及失败例子 | 根据是否需要深入 regex、特殊 token 拆分，不按文件数量拆篇 |
| 训练底座与基线 | 自动实验在训练什么，修改前应先保存什么 | nanochat 的实际训练、评测和运行脚本；autoresearch 的 `prepare.py` 与 `train.py` | 固定版本、数据、环境、配置、训练及验证输出 | 安装设置能与基线合并；不同硬件或训练阶段有独立验证时另立专题 |
| 固定评测与可比性 | 为什么使用这项指标，哪些条件必须不变 | autoresearch 的评测函数、固定准备部分与 `val_bpb` | 相同数据／评测条件下的基线和候选结果 | 指标解释与结果核查通常一起讲；涉及改变评测协议时单独说明 |
| 一次代码改动 | 改了哪一处，运行后得到什么，怎样保留或撤回 | autoresearch 的 `train.py`、`program.md` 及结果记录约定 | 差异、提交、执行日志、指标、失败或崩溃记录 | 一次改动形成闭环可作样篇；不能把修改前、修改后和看日志硬拆成三篇 |
| 外部 Agent 的实验循环 | 人定什么，Agent 做什么，哪些约定并非程序强制 | autoresearch 的 `program.md`，配合外部编程 Agent 的实际轨迹 | 请求／行动、文件变化、训练进程、评测与 Git 操作的一条完整轨迹 | 先讲单次闭环，再看有限多轮；没有新机制或独立证据就不另加篇目 |
| 结果分析与复现 | 一次较低指标能说明多少，怎样复查失败和代价 | 原项目的训练输出、实验表及保留／撤回约定 | 所有尝试、固定资源条件、重复核查、质量与资源分别报告 | 多轮才暴露的新问题可以拆；不靠成功截图或榜单凑一篇总结 |
| 进阶实现对照 | 同一机制换实现，哪些数值应该一致，哪些性能需另测 | nanoGPT 旧版训练实现；llm.c 的 CPU/CUDA 与 PyTorch 对照 | 相同问题的数值对照，或明确设备条件的性能实测 | 只有读者需要且资源可验证时选入；不是为了覆盖仓库名单而强行制作 |

每个工作包开写前都补齐「固定提交—文件／函数—实际输入—预期结果—失败分支—资源条件」。能对应到这些证据，再进入候选篇目；没有来源或没有验证条件的内容继续留在研究区。

## 主线中的角色必须按原作讲清

在 autoresearch 中，人编写或调整实验指令与边界；外部编程 Agent 按 `program.md` 阅读项目、修改允许的训练代码、运行实验、读取结果并操作 Git。`train.py` 是训练程序，不能因为它被 Agent 调用，就把它说成内部自带了完整的自主 Agent 循环。

`prepare.py`、评测条件与可修改文件的边界要按选定版本说明。「协议要求不修改」与「执行程序强制隔离」是不同证据；除非实际实现并验证了权限控制，不将一段提示词称为沙箱。

本次核查的 autoresearch 每次运行重新初始化训练模型，当前 `train.py` 没有保存 checkpoint；`keep` 留下的是候选代码提交，而不是继续训练上一轮权重。若要演示下载模型或接续训练，需要标明新增的权重保存设计。

原协议既有「指标更低才保留」的循环指示，也有允许等分但明显简化代码的原则。教学采用哪种判定应先写明，不能称为上游已实现的统一自动判断函数。崩溃记录的零分数是占位值，分析必须先区分状态。逐轮完整日志归档也需另加明确设计，不能把原版同名 `run.log` 当作自动保存的全部历史。具体依据见 [autoresearch 核查](源仓库核查/autoresearch.md)。

训练主张、人工操作、脚本执行和真实 Agent 行动分列。人工改一项参数并跑通，能证明实验流程；脚本重放能检查程序；只有真实外部 Agent 产生改动并取得反馈，才可说明它在该次任务中怎样行动。

## 首个制作任务：先读三份关键文件，再取得基线

首篇标题与期号暂不确定。先制作一份有原仓库锚点的样篇，拟问题是：「让 Agent 改训练代码之前，先固定什么？」

从 autoresearch 的 `prepare.py`、`train.py`、`program.md` 入手，画出数据／评测准备、训练、外部 Agent 协议三者关系。列明人修改什么、Agent 按约定修改什么、训练程序做什么，以及一次结果如何进入下一轮。

制作顺序是：固定提交并确认环境 → 按原入口完成准备 → 在约定硬件上取得一次训练基线 → 保存评测与完整日志 → 用实际证据写稿。若要在样篇中进一步展示 Agent 改动，则再增加一次受限的真实 Agent 尝试，同时保留失败情形，不能用人工修改或预写脚本代替。

| 验收对象 | 需要取得的证据 |
| --- | --- |
| 版本与文件分工 | 三份文件在同一提交，正文的可改／不可改范围与协议一致 |
| 训练基线 | 数据与准备记录、设备与依赖、原命令、退出状态、完整日志、验证指标 |
| 评测含义 | 能指出 `val_bpb` 的来源与比较方向，区分验证指标、训练损失与生成质量 |
| 实际用时 | 分清源码定义的训练计时预算、启动／编译、预热、验证和进程总时长 |
| 失败处理 | 安装／资源不足、训练崩溃、未产生有效指标均有真实状态，不删掉失败后只留最好一次 |
| Agent 闭环（若纳入样篇） | 外部 Agent 行动、实际代码差异、运行反馈、结果记录和保留／撤回依据完整对应 |

如果只完成阅读和手算，就交付代码阅读稿；如果只完成人工基线，就交付基线复现稿。命名和结论与证据匹配，不将两者包装为已完成 Agent 自动研究实测。

## 资源和费用不能沿用宣传数字

准备数据、训练 GPU、外部 Agent 调用及存储是不同的资源项，分别记录。源码中的固定训练预算不是整次进程时长，也不是外部 Agent 会话总预算。制作时先限定实验轮数与资源规模；若为教学加入原版没有的控制，明确标作本仓库的改编。

例如，本次版本的 300 秒训练计数排除了前 11 个确实进行参数更新的步骤，以及准备、初始化、最终验证等开销；在完整步骤结束时检查预算，也不是第 300 秒硬中断进程。协议中的超时处置由外部 Agent 执行，不是训练脚本内另有一个守护程序。正式文章按 [计时源码核查](源仓库核查/autoresearch.md) 和实际记录交代口径。

nanochat 的 CPU 缩小脚本只支撑对应缩小设置。不能据此承诺 autoresearch 原版在普通笔记本上直接运行，也不能把某次 GPU 租价下的成本估算当作人人可复现的当前报价。资源不足的读者可读源码、做小算例或核查保存的真实日志；这些学习活动与原版训练复现分开标注。

外部 Agent 的产品、模型、版本、接口和计费，在实际制作前从官方资料核查并记录，不在此猜选型或金额。本次没有调用模型服务、运行训练、申请 GPU 或产生费用测量。

## 篇数怎样逐步确定

1. **仓库核查：** 对齐版本、目录、入口和许可，剔除重复内容与已经过时的默认推荐。
2. **最小复现：** 先跑基线及一个有正反结果的改动，记录真正遇到的前提与失败。
3. **样篇试写：** 围绕一个完整问题写稿，检查正文是否能单独读懂、实验是否可跟随。
4. **拆并审查：** 需要新先修知识、独立实验或不同资源条件时拆；只是同一闭环的步骤时合并。
5. **形成目录：** 只给已确定的文章分配期号，更新累计篇目；资源支线与选读不自动占主线编号。

篇数因此是后续核查与制作的结果，目前仍为待定。既不把七仓库当成七篇，也不换一个固定数字继续凑篇数。

## 每篇最终交付与维护

公众号部分保留正文 Markdown、同步排版 HTML、标题摘要、必要机制图、双比例封面和网页入口。开发者部分必须链接原仓库固定提交、所读文件与函数、对应改动、可运行命令、环境和输入输出，并标清「原作者报告」「本仓库复现」「教学改编」。

复现使用原始仓库快照或有明确差异的改编版本，不把所有文章都指向变化中的最新分支。保存失败与全部尝试；如果迭代反复使用同一验证指标，要说明结论范围，另行验证时固定独立问题与检查条件。图中的数值要能回到对应记录，不能为了排版更换实验结果。

课程来源与素材的使用条件逐仓库记录；README 的许可声明不冒充已读取独立许可证文件，软件许可也不自动覆盖外部数据、视频或品牌图像。采用原代码或实质改编时，核对并保留适用的版权与许可说明。

维护时分别记录原仓库变更、改编代码变更、数据变化、外部 Agent 漂移和费用变化。CS329Z 只在确有需要时补充任务验收与评测方法，不重新变成本系列的主项目。
