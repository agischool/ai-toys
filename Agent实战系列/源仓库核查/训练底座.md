已实际查看的源码切面表明，目录名不能代替完整讲解：

- `tok_train.py` 默认使用约 20 亿字符、词表 32,768；`tokenizer.py` 用 rustbpe 训练、tiktoken 编码解码。这里不是逐行照搬 minbpe 的教学实现；前序分词基础可帮助读懂它，但无需把两套代码混成同一实现。
- `render_conversation` 除用户与助手边界，还处理 Python 请求及输出。用户文本不直接计回答损失；助手文本、Python 请求及助手结束标记可计分，工具输出的对应掩码为 0。`chat_sft.py` 再处理批次和目标，因此应沿编码→移位→损失查证，不能仅凭「SFT」这个名词推断掩码。
- `chat_sft.py` 从 `base` 加载权重，组合 SmolTalk、MMLU、GSM8K；`chat_rl.py` 从 `sft` 加载，在 GSM8K 上使用作者明确简化过的强化学习方法。不能把后一脚本写成包含独立奖励模型的标准 PPO/RLHF 全流程。
- `checkpoint_manager.py` 把 `base`、`sft`、`rl` 分别映射到 `base_checkpoints`、`chatsft_checkpoints`、`chatrl_checkpoints`。命令跑过但加载了另一种权重，不能算完成了所述阶段的对照。
- `engine.py` 不只有缓存：遇到 Python 边界 token 时可以调用其计算器逻辑，再把结果 token 放回生成序列。它不是先前服务台助手的通用工具注册框架，也不等于 autoresearch 的代码修改循环。本轮只读到相关分支，没有执行或审计其隔离效果。

## 实际资源要求与缩小路径

### nanochat 的完整配方与 CPU 配方要分开

`pyproject.toml` 标明 Python 3.10+，此固定版本指定 `torch==2.9.1`，通过 uv 的 cpu/gpu extras 选择依赖源；GPU 源指向 CUDA 12.8 轮子。这里只记录源仓库契约，没有验证本机兼容性。

`runs/speedrun.sh` 面向 8 张 H100 的单节点：先准备分词数据，再后台下载更多训练分片，随后训练、基础评测、SFT、聊天评测。当前实际命令是 depth=24、device batch=16，并启用 FP8。README 的目录示例注释仍出现 d20，不能据这条旧注释规定本系列规模。

脚本先下载 8 个分片训练分词器，注释估计约 800 MB 压缩文本；完整配方随后请求 170 个训练分片。后续下载、解压、评测与检查点仍要空间，不能把初始 800 MB 当作整次运行的磁盘需求。本轮没有下载，实际磁盘、峰值内存及端到端耗时仍待测。

README 的约 48 美元来自作者的算例：8 张 H100、约 2 小时、每 GPU 每小时约 3 美元。它对应作者的设备、租价与以 DCLM CORE 为参照的能力口径；不是本次报价、所有开销的上限，也不是普通电脑训练相同能力的承诺。README 其他位置与脚本还有约 1.5 小时等估计，定稿时应保留具体版本与条件，不能拼出一个保证值。

README 说可改为单 GPU、减小设备批次；这不保证显存总能容纳或耗时严格线性缩放。低于 80 GB 的设备尤其需要调整；跨平台路径也有作者未充分试过的部分。相关陈述目前只是上游说明，不是本仓库验证结果。

`runs/runcpu.sh` 是另一条教育路线：模型缩到 6 层、head dimension=64、上下文 512、设备批次 32、总批次 16,384、基础训练 5,000 步，再做 1,500 步 SFT。它仍先下载 8 个分片、以最多 20 亿字符训练分词器；「缩小模型」不等于没有数据准备。作者在 M3 Max 上的基础训练约 30 分钟、SFT 约 10 分钟，是指定设备的注释估计，且明确不应期待强结果。

`base_train.py` 顶部还有更小的 CPU/Mac 示例：4 层、设备批次 1、20 个优化步。它适合检查数据和更新链是否可运行，不等于完成 CPU 配方，也不能与完整 speedrun 的能力成绩直接比较。

### nanoGPT：保留旧版价值，但不要沿用旧环境和速度承诺

已读 [model.py](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py)、[train.py](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/train.py) 和 [字符模型配置](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/config/train_shakespeare_char.py)。核心路径是数据准备→`train.bin/val.bin`→`train.py`→`ckpt.pt`→`sample.py`；可从 scratch、resume 或 GPT-2 权重初始化。

字符模型可供理解因果模型、训练损失和采样，但不是完整聊天模型。README 的 CPU 缩小示例使用 4 层、4 头、128 宽、上下文 64、批次 12、2,000 步，并关闭 compile；其约三分钟与 MPS 加速倍数均是历史条件下的作者观察。不要按旧 README 的 nightly 建议直接规定 2026 年的安装环境。

README 的 GPT-2 124M 复现则是另一规模：8 张 A100 40 GB、约四天、OpenWebText。作者还说明它与原 WebText 有数据分布差异，需选合适基线；不能把「有一个 GPT 训练入口」写成和 nanochat speedrun 同样的任务与指标。

### llm.c：先做实现对照，GPU 性能另开分支

已读 [train_gpt2.c](https://github.com/karpathy/llm.c/blob/f1e2ace651495b74ae22d45d1723443fd00ecd3a/train_gpt2.c)、[test_gpt2.c](https://github.com/karpathy/llm.c/blob/f1e2ace651495b74ae22d45d1723443fd00ecd3a/test_gpt2.c)、[train_gpt2.cu](https://github.com/karpathy/llm.c/blob/f1e2ace651495b74ae22d45d1723443fd00ecd3a/train_gpt2.cu)、[Makefile](https://github.com/karpathy/llm.c/blob/f1e2ace651495b74ae22d45d1723443fd00ecd3a/Makefile) 相关入口及 [scripts/README](https://github.com/karpathy/llm.c/blob/f1e2ace651495b74ae22d45d1723443fd00ecd3a/scripts/README.md)。

CPU 示例从 GPT-2 124M 检查点开始，在短序列数据上更新并采样，不是普通电脑从零训练同能力模型。C 文件固定批次 4、序列 64；源码循环索引为 0 至 40，不能仅根据 README 的「40 steps」据写精确更新次数。正文若讲执行计数，应以对应代码与实际日志核对。

`test_gpt2.c` 使用 PyTorch 导出的权重及 debug state 核对数值与训练变化。适合先解释「同一计算换一种实现，怎样验证没算错」。运行 C 本体不依赖 PyTorch，不等于准备模型与参考结果也无需下载或 Python 依赖。

CUDA 主线使用 cuBLAS/cuBLASLt 等，cuDNN 为可选编译设置；多 GPU 还涉及 MPI/NCCL，跨节点涉及互联与启动方式。简化 FP32 CUDA 文件及 CPU 参考版保留了较早实现，不能当成当前高性能主线的等价资源路径。速度、显存与浮点一致性需要分别验证，不把 README 某个历史百分比当通用结论。

## 与 autoresearch 的真实关系

补查 autoresearch 固定提交 `228791fb499afffb54b46200aca536f79142f117` 的 [README](https://github.com/karpathy/autoresearch/blob/228791fb499afffb54b46200aca536f79142f117/README.md)：作者明确说其训练代码是 nanochat 的简化单 GPU 实现。研究循环以 `program.md` 提供实验规则，修改 `train.py`，依靠固定的 `prepare.py` 数据准备和验证工具评价变化。

因此，应把**可复核的训练与评测链**作为理解研究循环的依赖；不应把「先训练一个会聊天的模型」「先做完 RL」「先写完 CUDA 内核」都设成 autoresearch 的必要前置。研究 Agent 是修改训练代码的外部操作者，不是由 nanochat 训练出来的聊天模型自动变身。

nanochat 的 README 榜单反过来记录了 autoresearch 轮次带来的改进，这是项目之间的实际反馈关系；不表示任意一次自动尝试都能改善结果。

autoresearch 原版要求单张 NVIDIA GPU、Python 3.10+，测试硬件为 H100。每次训练预算五分钟，不含启动和编译，指标为 val_bpb。其原版 CPU/MPS 支持不能从 nanochat 的 CPU 脚本直接推定；README 指向小设备分支和适配建议，使用前要单独核查。这里只核查关系与训练前提，研究循环的具体控制与源码由相应核查文档继续展开。

| 读取模型与推理反馈 | checkpoint_manager、engine、chat_cli、infer_bench，依赖正确来源的模型和词表 | 追踪一次生成与必要的工具结果注入，核对缓存与终止；延迟/吞吐测试另记设备条件 | 会话格式、缓存正确性和计时若互相挤压则拆开；工具出现不代表要另造通用业务助手 |
| 可选的奖励驱动更新 | chat_rl、GSM8K、chat_eval，依赖 SFT 与可判分任务 | 说明奖励/优势与采样结果来源，记录实际更新与评测；不包装成完整 PPO/RLHF | 研究主线若只需基础训练指标，可暂不制作；只有与读者目标和资源匹配时扩展 |
| 接到自动研究循环 | autoresearch 的 prepare/train/program 与固定验证预算，依赖基础训练和评测 | 先有可复核的基线与单次候选对比，再讨论代码改动、保留/撤回及失败记录 | 不要求前置聊天 SFT/RL 或 llm.c；若输入契约不同，先做映射，不把 nanochat 命令直接冒充 autoresearch |
| 可选的底层数值与性能对照 | llm.c 的 CPU/PyTorch 对照，再到 CUDA；依赖前向/反向与数值容差理解 | 先核对相同输入、参数与目标的数值，再谈设备性能 | C 参考与 CUDA 优化可以分开；没有相同任务和数值基线时，不发布速度优劣结论 |

一条最小学习依赖是：数据与词表→基础训练→固定验证指标→一次受控改动→研究循环。对话 SFT、聊天评测与推理构成可选扩展，奖励驱动训练和 C/CUDA 又有各自前置；不应被线性清单强行绑成人人必修。
