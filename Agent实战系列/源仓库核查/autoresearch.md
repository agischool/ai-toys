## 原项目的研究对象是什么

它给外部编码 Agent 一个小型、真实的语言模型预训练设置，让 Agent 改 `train.py`、运行一次训练、读取固定验证指标，再决定保留还是撤回代码变化。人主要通过 `program.md` 安排研究规则。

**一次尝试的核心对象是训练代码及其产生的模型结果。** 这不是邮件/工单助手，不是先设计一套任意工具调用演示，也不是训练那个负责修改代码的外部大模型。

需要特别写清两件事：

1. 每次执行 `train.py` 都设置随机种子 42、创建模型、初始化权重并创建优化器；没有加载上一轮模型权重继续训练的代码。「下一次实验」是在新进程中重跑候选训练方案。见 [train.py 第 457—510 行](https://github.com/karpathy/autoresearch/blob/228791fb499afffb54b46200aca536f79142f117/train.py#L457)。
2. 当前 `train.py` 没有保存训练权重 checkpoint。`keep` 留下的是通过 Git 管理的代码提交，`results.tsv` 留下成绩记录。若教学想让读者下载某轮模型或继续训练，须另加明确的权重保存设计，不能写成原版现成能力。

固定种子便于比较，但不等于已经做过多种子重复实验，也不保证不同硬件和实现完全确定。连续用同一验证集选方案，还需要防止把验证分数改善泛化成独立测试能力提升。

## 人、编码 Agent 与运行程序的真实分工

| 角色 | 原仓库安排的工作 | 不应误写成什么 |
| --- | --- | --- |
| 人 | 准备机器与依赖，先完成数据准备；与 Agent 确认新运行标签及初始化；编辑 `program.md` 中的研究目标、边界和取舍；需要结束时中断 | 只发一句话就自动获得 GPU、数据、费用额度及完整实验系统 |
| 外部编码 Agent | 读取仓库和 `program.md`，建立新研究分支，先运行未改基线；修改 `train.py`、提交、启动进程、读日志、维护结果表、决定保留或撤回；识别崩溃和超时 | 被 `train.py` 训练出来的模型，或仓库已经实现的另一个 Python 调度器 |
| 外部 Agent 客户端、终端与 uv | 提供读写文件、Git 和启动/停止进程等执行能力；uv 解析项目环境并启动训练脚本。Agent 使用哪个模型、怎样获得模型服务，由该客户端另行配置 | `pyproject.toml` 内置的 Claude/Codex 研究执行器或自动云部署服务 |

| `train.py` / PyTorch / GPU | 在一次进程中完成模型初始化、训练、最终验证和摘要打印 | 自己提出实验想法、自动循环 Git 提交，或在内部自动作 keep/discard 决策 |

根目录没有独立的研究循环脚本；循环写在给 Agent 阅读的 `program.md` 里。README 建议启动 Claude、Codex 等外部工具，本身没有把某个 Agent SDK 列为依赖。`program.md` 中的无限循环与超时处理是对外部 Agent 的指示，不是操作系统级守护程序。

## 五分钟到底计算了什么

README 将其称为排除启动/编译的五分钟训练预算；细读实现，还要说明以下口径。

- [prepare.py 第 30—32 行](https://github.com/karpathy/autoresearch/blob/228791fb499afffb54b46200aca536f79142f117/prepare.py#L30) 固定 `TIME_BUDGET=300` 秒。
- 每个完整优化步骤，脚本在 CUDA 同步后记开始时间，执行梯度累积、取下一批数据、调度学习率、优化器更新和梯度清零，再同步 GPU 取结束时间。
- **只有进入步骤时 `step > 10`，这个步骤的耗时才加到训练预算。** 当前计数从 0 开始，所以索引 0—10 的前 11 个完整训练步没有进入 `total_training_time`。它们仍更新了参数；不能称为「没有训练的纯编译等待」。见 [train.py 第 543—604 行](https://github.com/karpathy/autoresearch/blob/228791fb499afffb54b46200aca536f79142f117/train.py#L543)。
- 累计值达到 300 秒后，在当前完整步骤结束时退出，并非精确到第 300 秒强行中断当前步骤，因此可以略超预算。

| 项目 | 进入 300 秒计数吗 | 说明 |
| --- | --- | --- |
| 安装依赖、下载数据、训练分词器 | 否 | 在训练脚本之前另行准备 |
| Python 导入与内核加载 | 否 | 其中部分发生在 `t_start` 之前，连输出的 `total_seconds` 也不一定覆盖 |
| 模型初始化、优化器建立、首次取批 | 否 | 发生在训练循环之前 |
| 前 11 个完整训练步 | 否 | 用来避开早期编译/热身影响，但这些步骤确实更新参数 |
| 后续完整训练步内的数据加载、前反向、更新、同步 | 是 | 按该步骤的 `dt` 累加 |
| 步骤计时区间外的日志打印与 GC 管理 | 否 | 发生在本步 `t1` 之后 |
| 最后 `evaluate_bpb` 验证 | 否 | 训练结束后另跑验证 |
| Agent 思考、改代码、Git、读结果、决定下一步 | 否 | 外部研究循环的工作 |

因此不能写「每五分钟必定完成一个实验」「睡八小时必得约一百次结果」。README/指令中每小时约 12 次、整夜约 100 次是粗略设想，实际还包含上述开销、故障与 Agent 用时。

`program.md` 另要求某次运行超过 10 分钟时杀掉进程，按失败处理。这个要求由外部 Agent 执行；训练脚本没有另建 10 分钟 watchdog。`training_seconds`、`total_seconds` 与整个 Agent 循环用时是三个不同口径。

## val_bpb、固定评估与保留/撤回

### 指标怎样得到

`evaluate_bpb` 在冻结的 `prepare.py` 中：累计每个目标 token 的交叉熵，使用自然对数计量；查表累计目标 token 对应的字节长度；字节长度为 0 的特殊 token 从两项累计中排除；最后返回：

```text
val_bpb = 有效目标的交叉熵总和 /（ln(2) × 有效目标字节总数）
```

结果的单位是 bits per byte，越低越好。它是在验证文本上的预测指标，不是回答任务正确率，也不是一段生成文本的人工质量评分。原版以字节归一的方式减少 token 粒度对指标口径的影响，但**在这套正常研究规则中，分词器本来就是冻结的**，不能据此授权 Agent 改分词器或验证集。见 [prepare.py 第 340—365 行](https://github.com/karpathy/autoresearch/blob/228791fb499afffb54b46200aca536f79142f117/prepare.py#L340)。

固定数据与评估设置：

- 数据源是 `karpathy/climbmix-400b-shuffle`，下载地址在 `prepare.py` 中；默认准备前 10 个训练分片，外加固定的 `shard_06542.parquet` 验证分片。不是默认下载整个 400B 数据集。
- 分词器训练与训练加载器都排除该验证分片；验证加载器只读这一固定分片。
- `MAX_SEQ_LEN=2048`；`EVAL_TOKENS=40×524288=20,971,520`。验证步数实际用整数除法 `EVAL_TOKENS // (batch_size×2048)`。默认 batch 128 时为 80 批；任意改配置时，须核对实际取整后的覆盖量。
- `VOCAB_SIZE=8192`，包括四个保留特殊 token；训练 BPE 的数据迭代默认最多约十亿字符，每个文档最多取一万字符。分词产物与数据缓存在 `~/.cache/autoresearch/`。

这是一份反复用于选方案的固定验证设置，原版没有另外执行独立最终测试、置信区间或多种子显著性检验。小幅降低只证明该次记录的验证分数更低。

### 谁做 keep/discard

按照 `program.md`，外部 Agent 的循环是：

1. 查看当前分支与提交，提出一个改动并修改 `train.py`。
2. Git 提交候选改动，再运行 `uv run train.py > run.log 2>&1`。
3. 从摘要中读取 `val_bpb` 与显存，失败时查看日志尾部。
4. 在 `results.tsv` 记录短提交号、分数、显存、`keep` / `discard` / `crash`、说明；这个表按原指令保持未跟踪、不提交。
5. 若方案被保留，留在候选提交继续；若分数不改善，回到改动前的提交。不可用的尝试记为失败，之后继续尝试。

这里有一个应明确给读者看的原文张力：循环步骤要求「更低才保留，相同或更高则撤回」；前面的简洁性原则又允许「成绩相同但代码明显更简单」作为保留理由。**这不是训练脚本里已经统一实现的自动判定函数**。正式教学应先与读者约定：本轮用严格分数规则，还是允许另行说明的简洁性例外；记录采用了哪一种。

崩溃在 TSV 中按指令把分数填为 `0.000000`、显存填为 `0.0`。这是占位值，不是比正常结果更好的零 BPB；分析时必须先看 `status`。原指令每轮重定向到同一个 `run.log`，并不自动归档每轮完整日志。若本系列要求可追查的完整记录，应另定按提交号保存日志的教学补充规范，并标明这部分是新增设计。

## 哪些文件能改，哪些规则被冻结

| 对象 | 原版正常实验的边界 | 教学上的处理 |
| --- | --- | --- |
| `train.py` | Agent 可以改模型结构、优化器、超参数、训练循环、batch、模型规模等 | 每次优先提出一个能解释的实验假设，再看差异和结果；不要把同时大量改动说成已定位单一原因 |
| `prepare.py` | 禁止 Agent 修改；评估、数据加载、分词器和训练常量被冻结 | 原版复现时不改；改变后应另列实验设置，重新建立基线 |
| `program.md` | README 将它列为人编辑的研究指令；Agent 按它做实验 | 可以围绕原研究目标打磨假设、记录和取舍，不将任意业务助手指令替换成原项目 |
| `pyproject.toml` / 新依赖 | Agent 不得安装新包或加依赖，只使用已有项目依赖 | 环境由人在开始前准备；不能为某次候选默默换依赖来占便宜 |
| 数据、分词缓存与验证口径 | 先准备好，再保持冻结 | 避免将旧缓存、不同数据分片或改过的 tokenizer 混在一个比较表中 |
| `results.tsv` / `run.log` / Git 分支 | 虽然不是研究代码，Agent 仍需要创建或更新它们 | 「只改一个文件」指候选训练代码，不是声称整个研究过程从不写其他文件 |

这些边界主要是给编码 Agent 的指令，仓库没有提供把 `prepare.py` 设成 OS 只读、禁止读取验证数据或自动校验基准文件哈希的独立执行隔离层。文章应说「按约定冻结」，不要写成「程序保证它绝不可能改动」。

README 的小硬件移植建议确实提到降低 `prepare.py` 的序列长度、词表和评估量。这属于另建移植版本的配置设计，与同一轮正常实验中「不改 prepare.py」有不同范围。移植后要重建基线，不能把两个设置下的成绩直接塞到原版同一张表。

## 硬件、依赖、默认值与费用

### 实际运行设置

| 项目 | 该提交默认设置或声明 |
| --- | --- |
| 硬件 | README 要求一张 NVIDIA GPU，作者在 H100 上测试；没有声明任意低显存 GPU 都能跑默认配置 |
| 平台实现 | 直接使用 CUDA；没有原生 CPU/MPS 回退路径。Mac 等分支在 README 另行链接，不能混称原仓库同一实现 |
| Python | 项目声明 `>=3.10`；本轮未据 `.python-version` 声称更具体的环境要求 |
| PyTorch | `torch==2.9.1`，uv 指向 CUDA 12.8 的 PyTorch 包索引；不是标准库项目 |
| 其他直接依赖 | kernels、matplotlib、numpy、pandas、pyarrow、requests、rustbpe、tiktoken；具体下界见 pyproject |
| 注意力内核 | 运行时通过 `kernels.get_kernel` 取得 Flash Attention 接口；Hopper 能力 `(9,0)` 选 `varunneal/flash-attention-3`，其他能力选 `kernels-community/flash-attn3` |
| 精度与编译 | CUDA bfloat16 autocast；`torch.compile`，编译和内核条件需在实际设备核实 |
| 模型 | 实际脚本 `DEPTH=8`；按深度和 `ASPECT_RATIO=64` 算出维度 512；`HEAD_DIM=128`，由此四个注意力头及四个 KV 头；窗口模式 `SSSL` |
| 训练 batch | `TOTAL_BATCH_SIZE=2**19=524,288` token/优化步；`DEVICE_BATCH_SIZE=128`，每次前反向 `128×2048=262,144` token，因此默认梯度累积两次 |
| 优化器 | Muon 与 AdamW 组合；矩阵学习率 0.04、token embedding 学习率 0.6、输出头学习率 0.004，更多参数在 train.py 中 |
| 显存 | 作为允许权衡的软约束，结果表记录峰值分配显存；README 未给出一个适用于所有配置的硬性最低显存值 |

不要误取 `GPTConfig` 数据类中的通用默认层数/维度作为这份脚本实际运行配置；真实入口会用 `build_model_config(DEPTH)` 覆盖。`mfu_percent` 使用 H100 BF16 理论峰值常数作分母，在别的 GPU 上不能未经调整当成该卡准确的利用率。

### 上下游依赖及成本证据

- 训练代码从 Andrej Karpathy 的 [nanochat](https://github.com/karpathy/nanochat) 挑选并简化；读懂小 Transformer、分词、优化器和验证指标是学习依赖，不意味着必须按清单顺序跑完 Karpathy 的所有仓库。
- 前置要有依赖环境、足够 GPU/显存与磁盘、Hugging Face 数据和内核来源的访问条件。下载与首次分词的实际用时依赖机器和网络；README 的「约两分钟」不是本地实测保证。
- 外部编码 Agent 还有自己的模型服务、账号或本地运行条件，其费用不在 `train.py` 的输出里，也不由这个仓库管理。
- 原版没有 GPU 租赁价格表、GPU 预算上限或整夜总费用限制。需要真实运行前另行确认硬件计价与 Agent 计费；`300 秒×次数` 只是训练计数，不能充当完整账单。
- 不把 nanochat 在另一套硬件/目标下的约 48 美元估算移植到 autoresearch，也不从 README 的「一夜约百次」推导包价。

编辑建议：实际实验报告应分别记录一次性准备、进程完整用时、GPU 计费时长、Agent 的调用或订阅消耗，以及失败运行。没有这些记录时，只能说明需要哪些资源，不能给出本项目「实测成本」。

## 许可核查

README 末尾明确写「MIT」，但此固定提交的根目录没有 `LICENSE` 文件，GitHub 读取该路径失败；`pyproject.toml` 也没有补上完整许可文本。**本轮能确认的是作者在 README 中作了 MIT 标注，不能写成已读到独立 LICENSE 及完整版权声明。**

技术讲解应链接原作者与固定提交。若后续要把大段源码、文件或改编实现打包发布，须再核对原仓库明确的许可文本、版权声明与所用数据、内核等各自条件；不能把源码 README 的 MIT 标注推广为所有外部资源的统一许可。

| 工作单元 | 读者实际要做或看懂什么 | 适合合并/拆开的条件 | 何时必须实际跑 |
